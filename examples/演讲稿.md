# 演讲稿：Agent 核心模块介绍

---

## 开场（1分钟）

大家好，今天我来给大家介绍这个 Agent 项目的三个核心模块：**tools.py**、**cli.py** 和 **session.py**。

简单说一下背景：这是一个 Python 实现的 ReAct Agent CLI。ReAct 是什么？就是我给 Agent 一个问题，它不是直接回答，而是会先思考（Reasoning），然后调用工具去执行（Acting），得到结果后再思考、再行动，循环直到得到最终答案。

整个项目就是围绕这个循环运转的，而今天要讲的三个模块，分别承担了**工具执行**、**用户交互**和**会话管理**的职责。

---

## 一、tools.py — Agent 的手和眼（3分钟）

第一个模块是 **tools.py**，这是 Agent 与外部世界交互的桥梁。

### 1.1 工具注册机制

传统的工具调用大家可能见过那种传一个字符串名字然后 switch-case 的写法，但我们这个项目用的是**装饰器模式**。看这个例子：

```python
@tool(
    name="read_file",
    description="读取文件内容并返回",
    schema={...}
)
def read_file(args: dict, ctx: ToolContext) -> str:
    # 读取逻辑
    return content
```

用 `@tool` 装饰器一装饰，这个函数就自动注册到 `TOOL_REGISTRY` 里了。好处是什么？工具的名称、描述、参数 schema 这些元信息全部内聚在函数本身，你看到任何一个工具函数，就知道它叫什么、干什么、参数是什么，不用到处找配置文件。

### 1.2 ToolContext

每个工具函数的签名是固定的：`(args: dict, ctx: ToolContext) -> str`。第二个参数 `ToolContext` 是**运行时状态**，这里面有两个关键字段：`work_dir` 和 `session_id`。

`work_dir` 是可变的。比如用户说"切换到 docs 目录"，Agent 就会调用 `change_dir` 工具，这个工具会修改 `ctx.work_dir`。之后 Agent 再调用 `read_file` 工具时，传入的相对路径就会基于新的工作目录来解析。

这就是为什么 `change_dir` 必须是一个工具而不是配置文件，因为它是**运行时动态改变状态**的行为。

### 1.3 内置工具

项目内置了 6 个工具：

| 工具名 | 功能 |
|--------|------|
| `read_file` | 读取文件内容 |
| `write_file` | 写入文件内容 |
| `list_dir` | 列出目录 |
| `change_dir` | 切换工作目录 |
| `shell` | 执行 shell 命令 |
| `search_files` | 搜索文件 |

这些都是 Agent 最基础的能力，让它可以读写文件、操作目录、执行命令。

### 1.4 执行流程

当 LLM 返回 tool_calls 时，AgentLoop 会调用 `execute_tool()` 函数。这个函数做三件事：根据名称查找工具、解析参数 JSON、执行函数。如果执行过程中抛出异常，它会**捕获异常并返回错误字符串**，而不是让整个循环崩溃。这个设计保证了 Agent 的健壮性。

## 二、cli.py — 用户界面（2分半钟）

第二个模块是 **cli.py**，这是用户和 Agent 交互的界面。

### 2.1 REPL 主循环

CLI 的核心是一个 `while True` 循环：读取用户输入 → 判断是斜杠命令还是普通消息 → 分别处理。斜杠命令以 `/` 开头，比如 `/help`、`/session new`、`/history` 等；普通消息则发送给 AgentLoop 处理。

### 2.2 斜杠命令系统

斜杠命令分为几类：

**会话管理**：
- `/session new` — 创建新会话
- `/session list` — 列出所有会话
- `/session load <id>` — 切换会话
- `/session info` — 查看当前会话信息
- `/session delete <id>` — 删除会话

**调试辅助**：
- `/history` — 查看对话历史摘要
- `/clear` — 清空历史但不删除文件
- `/tools` — 列出所有可用工具及状态
- `/config` — 显示当前配置

**导航**：
- `/cd <path>` — 切换工作目录

### 2.3 彩色输出

项目用了 `colorama` 库实现跨平台彩色输出：

| 颜色 | 用途 |
|------|------|
| 灰色 | 工具调用和工具结果，干扰信息所以用暗色 |
| 红色 | 错误信息，需要醒目 |
| 蓝色 | 系统提示和标题 |
| 绿色 | 启用状态 |
| 黄色 | Session ID |

### 2.4 readline 历史

项目还支持 `readline`，实现两个功能：第一是**上下键**浏览历史输入，跨会话持久化；第二是 **Tab 补全**斜杠命令，提高输入效率。

## 三、session.py — 记忆系统（2分半钟）

第三个模块是 **session.py**，这是 Agent 的记忆系统。

### 3.1 为什么需要 Session

如果你和 Agent 聊了半天，回头想继续这个话题，没有持久化的话对话就丢了。Session 就是来解决这个问题的——它把对话历史存到文件里，下次可以恢复。

### 3.2 数据结构

项目里有两个核心数据结构：`Session` 和 `SessionMeta`。

`Session` 包含 ID、创建时间、更新时间、标题、消息历史。其中标题是自动从第一条用户消息生成的，最多取前 30 个字。

`SessionMeta` 是给索引用的轻量版，用于列表展示，不包含完整的消息历史。

### 3.3 Session ID 格式

Session ID 的格式是 `YYYYMMDD-HHMMSS-<6位十六进制>`，比如 `20260420-143022-a3f7b1`。时间戳保证基本唯一，末尾的随机字符进一步降低碰撞概率。

### 3.4 持久化存储

存储结构是这样的：

```
.sessions/
├── index.json              # 索引文件
└── 20260420-143022-a3f7b1.json  # 各会话详情
```

每保存一次 Session，会同时更新 session 文件和 index 文件。Index 的作用是快速列出所有会话而不需要扫描目录。

### 3.5 生命周期

启动时根据参数决定行为：无参数创建新 Session、`--resume` 恢复最近一次、`--session <id>` 恢复指定会话。每轮对话结束后，如果 `auto_save=true`，会自动保存。下次启动可以无缝衔接。

## 总结（1分钟）

最后用一张图来总结三个模块的关系：

```
cli.py（用户界面）
      ↕
AgentLoop（核心循环）
      ↕
tools.py ↔ session.py
（工具执行）  （会话管理）
```

具体来说：cli 接收输入 → 调用 AgentLoop 处理 → AgentLoop 需要操作文件时调用 tools → AgentLoop 需要保存对话历史时调用 session。

三个模块各司其职，通过清晰接口通信，这就是整个项目的基本架构。
